# ocms 决策记录规则

本文件定义「什么情况下该记录决策，以及如何记录」。它是决策链（DecisionGraph）的客观规范。

## 一、什么算「有意义的决策」

只有满足下面任一条件，才值得记录为一个决策节点：

1. **方案取舍**：你在多个方案之间做了选择，或明确否掉了某个方案。
2. **反复磨合**：同一个问题 / 做法被来回调整多次后，最终确定了一个做法（说明背后有隐含的取舍）。
3. **方向性决策**：选型、架构、策略、路线等会影响后续行为方向的决定。
4. **约束与约定**：确定了一条会约束后续行为的规则、约定或边界（如「统一用 X 而不是 Y」）。
5. **显式要求**：用户明确说「记住这个」「记下这个做法」等。

## 二、什么「不算」决策（不要记录）

- 小改动：换个说法、微调细节、格式化。
- 无争议的常规操作：照着既有模式做，没有「选择」的空间。
- 一次性、不产生后续影响的操作。
- 用户随口一提、尚未确定的意向（这类属于「待定」，除非用户明确拍板）。

**原则：宁缺毋滥。** 不确定时，不记录。

## 三、决策节点字段规范

记录决策时，各字段按如下填写：

| 字段 | 说明 | 要求 |
|------|------|------|
| `chain` | 决策链名（文件夹名） | 相关决策归入同一条链，如 `api-design`、`product-strategy` |
| `decision` | 做了什么决定 | **一句话概括**，简洁且描述清楚——这是未来检索决策时读的「摘要」字段 |
| `rationale` | 为什么这么做 | 核心理由，说清「因为什么」 |
| `trigger` | 什么触发了这个决策 | 可空；如「用户反馈 bug」「效果不达预期」 |
| `alternatives` | 被否掉的备选方案 | 数组，每项含 `option`（方案名）+ `why_not`（为什么否掉） |
| `taste_signals` | 这个决策反映的品味偏好 | 数组，每项含 `signal`（偏好名）+ `context`（如何体现） |
| `supersedes` | 推翻/取代了哪个旧决策 | 被取代的旧决策节点 id，可空 |
| `caused_by` | 因果链：这个决策的直接前因 | 前一个决策节点的 id，可空 |

## 四、因果链关联

决策之间可以形成「因果链」。**关键：同一件事的持续讨论，不是「覆盖」旧决策，而是「追加」新节点、串联起来。**

- **caused_by**：当前决策是「因为」某个前序决策（或其暴露的问题）才产生的，就填那个决策的 id。
- **supersedes**：当前决策「修改/取代」了某个旧决策的结论，就填旧决策的 id。同一话题反复讨论中，后面一轮的共识如果改动了前面一轮，用 `supersedes` 关联；旧决策的 outcome 会被自动标记为 superseded。

**注意**：`caused_by`（前因）和 `supersedes`（取代）语义不同，不必强行同时填。只有在关系明确时才填，不要为了「链而链」。
