# ocms 事件记录心法

本文件讲「怎么识别、记录、管理事件」。字段规范和「什么算事件」见 `.ocms/rules/_sync_event.rule.md`，这里不重复。

## 事件是什么

事件 = 你和用户之间「发生了什么」的**结构化摘要**。它解决的是**对话连续性**：重启会话后，你还能接上之前聊过的话题，知道「聊到哪了、为什么停在这」。

事件不是流水账。原始对话记录由 OpenClaw 自己写（`memory/*.md`），事件只存**摘要 + 状态 + 关系 + 指针**，指向原始记录方便回溯。

## 事件的生命周期（核心）

事件按「话题」分。一个话题 = 一个事件。话题可大可小：

- **大话题**：跨度长、内容多，需要**分组管理**（一个父事件下挂多个子事件）。
- **小话题**：独立、简短，正常存一个事件。

**关键：事件有「开」和「合」，但可以「只开不合」。**

```
事件状态：
├─ OPEN（进行中）    — 正在聊，有继续的预期
├─ ASKED（已询问）   — 话题转向后已问过用户，等待回应
├─ CLOSED（合）      — 用户明确「继续并聊完」或「不聊了」
└─ DORMANT（沉底）   — 用户没回应，标记后不再主动管
```

### 状态的流转规则（务必记住）

1. **「合」是被动产生的，不主动封口**。没有「超时强制合」，只有用户明确表态才 CLOSED。

2. **话题转向时，立即询问**。当你和用户正在聊话题 A，用户突然转向话题 B，且话题 B 聊完后，你要**当场（同一轮里）自然地问一句**：「对了，之前聊的 A 话题还要继续吗？」——**不要等到下次会话**。问完立刻把 A 标记为 ASKED。

3. **对话突然中断时，下次会话开场主动询问**。如果对话突然中断（用户聊完直接走了、没有收尾），事件停在 OPEN（只开未合）。**下次会话开始时**，查「进行中事件」（`ocms_event_list`），对其中 OPEN 状态的事件，**主动询问用户**「上次的 X 话题还要继续吗？」——因为中断时用户已不在场，只能下次开场补问。

4. **询问只有一次机会**。问过就标记 ASKED，之后无论结果如何，**不再重复提醒**。避免每次都唠叨「那个话题还继续吗」。

5. **三种结果**：
   - 用户「继续」→ 事件回到 OPEN，继续聊。
   - 用户「不聊了」→ 事件 CLOSED。
   - 用户沉默没回 → 事件 DORMANT（沉底），不再主动唤起。除非用户**之后主动聊起**相关话题，否则它只安静躺在历史记录里。

6. **唤起方式**：接续话题时，先查「最近的 OPEN/ASKED 事件」（用 `ocms_event_list`），不要大海捞针。只有用户主动提起某个久远话题时，才用 `ocms_event_recall` 向量检索历史事件。

### 状态语义提醒（重要）

- **OPEN** = 待接续（可能因突然中断）。**下次会话开场应主动询问用户是否继续。**
- **ASKED** = 已问过用户，**不再重复问**，等用户主动提。
- **CLOSED** = 已闭环。
- **DORMANT** = 沉底，不主动唤起，除非用户主动聊起。

### 对话结束时的判断（每次对话收尾时做）

对话收尾时，问自己：**这次对话结束了吗？**

- **已闭环** → 整理这次聊的话题摘要，存成事件（新事件 OPEN 转 CLOSED，或更新已有事件）。
- **还没结束** → 事件保持 OPEN，等下次对话继续。不要急着封口。

## 怎么记录

识别到要记录/更新的事件时，用 `ocms_event` 工具：

1. 给事件起一个**一句话标题**（未来检索的摘要字段）。
2. 写一段**摘要**（这次聊了什么、结论是什么、停在哪）。
3. 定**状态**（见上面的流转规则）。
4. 判断**话题大小**：大话题用 `parent` 挂到父事件下分组，小话题独立存。
5. 填**关系**（见下）。

## 事件的关系（记录时顺手判断）

事件不是孤立的。记录事件时，顺手判断两条关系：

### 1. 产生了什么决策？（事件 → 决策）

「决策从事件中产出」。如果这次对话里产生了新决策，在事件里记下这些决策的 id，把「事件」和「决策」关联起来。这样未来的你能追溯：**这个决策是在什么上下文里做出的**。

### 2. 和之前哪些事件有关？（事件 → 事件，单向「影响」）

多个事件之间可能存在「影响」关系——A 事件影响/推动了 B 事件。判断标准：

- **单向**：时间线性单向，A 影响 B，B 不反向影响 A。
- **不分强度**：只要「有关」就关联，不用判断影响多大。
- **多对多**：一个事件可以影响多个事件，也可以被多个事件影响。

**注意区分**：「影响」是事件之间的关系，**不是「谁产出谁」的因果**。因果产出（事件产出决策）用「产生自」关系；事件之间的关联用「影响」关系。两者语义不同，别混。

## 指针：指向原始记录

每个事件摘要，都要记下它对应的**原始流水账位置**（`memory/YYYY-MM-DD.md` 的段落），方便未来回溯完整上下文。

- 用段落标题或一段独特的锚文本定位，不用行号（行号会因追加而偏移）。
- **重要**：指针可能不准确（原始文件可能被改动）。未来用到指针时，**先核对，对不上就从粗粒度（关键词/向量）重新检索**，不要硬信任指针。

## 原则

- **摘要优先，不抄流水账**：只记提炼后的结论和上下文，原文留在 OpenClaw。
- **状态诚实**：不为了「好看」而乱封口，聊到一半就是 OPEN，没下文就是 DORMANT。
- **自然不打扰**：顺手记录，不打断任务、不长篇汇报。
- **宁缺毋滥**：不确定是否值得记的事件，先不记。
