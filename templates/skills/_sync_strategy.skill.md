# ocms 同频记忆引擎

ocms（openclaw-mesync）是运行在 OpenClaw 里的 **Agent 级记忆插件**。它的目标是：**让你和用户（以及你自己的历史）保持「同频」**——记住你做过哪些决策、形成了哪些认知、沉淀了哪些品味、经历了哪些事件，让未来的你不再重复犯错、不再反复踩坑、重启会话也能接上之前聊过的话题。

有了这些，你做任何事情（查资料、做判断、写代码、做产品、与人沟通）时，都能调用过去的经验，保持一致性与成长。

## 记忆模型：四块内容，各管一件事

**文件位置约定（重要）**：ocms 的所有文件都存放在**当前 Agent 的 workspace 目录下的 `.ocms/` 目录**里（具体路径由 ocms 用 `resolveAgentWorkspaceDir` 解析得到，通常是 `~/.openclaw/workspace-<agent-id>/.ocms/`）。下文提到的 `cognition/xxx.md`、`taste/xxx.md`、`decisions/<链名>/`、`events/`，都在这个根目录下。用 `read` 工具读这些文件时，请用完整路径。

ocms 的记忆由四部分组成。**判断一条信息属于哪块，用各自的「判断标准」，四者不互斥——一条信息可以同时属于多块，不要四选一。**

| 内容 | 回答什么 | 存在哪里 | 判断标准 |
|------|---------|---------|---------|
| **认知（Cognition）** | 世界「是什么、怎么运作的」 | `.ocms/cognition/` 的 md | 客观知识、方法论、领域规律，不依赖用户偏好 |
| **品味（Taste）** | 用户/你「偏好、倾向什么」 | `.ocms/taste/` 的 md | 涉及审美、风格、判断倾向——「将来做类似事，会不会希望保持一致」 |
| **决策（Decision）** | 「为什么这么定、取舍了什么」 | `.ocms/decisions/<链名>/` | 有取舍、有因果的选择 |
| **事件（Event）** | 「发生了什么事、聊到哪了」 | `.ocms/events/` | 一次有实质的对话话题的摘要，解决「对话连续性」 |

### 关键：四者不互斥，会重叠

一条信息往往**同时**属于多块。例如「写代码时组件 API 要简洁」：

- 它是**决策**（「定了 API 设计原则」——为什么、舍弃了什么）
- 它也是**品味**（「对 API 设计的审美偏好」——将来做类似设计要一致）
- 它还可能是一条**认知**（「简洁 API 更易维护」这个客观规律）

**正确做法是各记各的，不要因为「已经记了决策」就跳过品味或认知。** 判断时，用上面的「判断标准」对每一块独立判断，沾边就记。

### 四块的关联关系

- **决策 ↔ 品味**：决策节点的 `taste_signals` 字段记录「这个决策反映了什么品味」（因果边）。品味的详细内容落到 `taste/`。
- **决策 → 认知**：决策往往沉淀出新认知，从而反映到 `cognition/`。
- **品味 → 决策**：品味沉淀后，反过来指导将来的判断和决策。
- **事件 → 决策**（产生自）：决策从事件中产出，事件是决策的上下文根。记录决策时，关联到触发它的事件。
- **事件 → 事件**（影响）：事件之间有单向的「影响」关系（多对多，不分强度）。

> **事件是新增的一块**，它和决策/认知/品味的区别：决策/认知/品味回答「为什么、怎么做、什么偏好」，事件回答「发生了什么、聊到哪了」。事件解决的是**对话连续性**——重启会话后能接上之前的话题。详见 `.ocms/skills/_sync_event.skill.md` 和 `.ocms/rules/_sync_event.rule.md`。

### 品味的「两层」结构（务必配套）

品味有**两层**，都要做：

1. **关联层**：决策里的 `taste_signals` 字段（记录「决策 → 品味」的指针）。
2. **落盘层**：`taste/<分类>.md` 的详细内容（品味的完整描述 + 来源）。

**记了 `taste_signals`，就要配套落到 `taste/`。只填字段不落盘是「只记了半层」。**

## 完整的工作闭环

### ① 做事：参考记忆

做事时主动参考认知（知识、方法论）和品味（审美、偏好），产出与过去一致、不重复犯错。

### ② 开场：接续未完成话题

对话开场时，先查「进行中事件」（`ocms_event_list`），看有哪些话题还没聊完。对其中 **open** 状态的话题，**直接带出上下文、自然延续**（「接着上次的 X，我们继续…」），**不要询问**「要不要继续」——用户回来（或被迫重启会话回来）就是来继续的。对 **asked** 状态的话题，不重复问，等用户主动提。这是对话连续性的关键——重启会话后，你要能接上之前聊到一半的话题。

### ③ 决策：拉取历史，选择匹配的方案

面对多种方案时，先用 `ocms_recall` 查历史决策、参考品味，选择高度匹配的方案，不要凭空拍板。检索决策用二级方式：先 `ocms_recall`（看决策摘要列表），再 `ocms_recall_detail(id)` 读完整决策。

### ④ 反馈：处理肯定与否定，演化决策

- **用户肯定** → 决策在当前场景成立，自然继续。
- **用户否定** → 这是最重要的信号。回看当初的 rationale 向用户澄清，引导用户说明否定原因（背后必有场景差异），达成新共识后**追加一条新决策**（`caused_by`/`supersedes` 关联旧决策）。

  核心：**「加深印象」不是调权重，而是延伸决策链**——每次否定都说明场景有差异，差异要用更多决策节点记录。

### ⑤ 收尾：封口事件（辅助，不是唯一记录时机）

**核心：事件要在对话推进中持续记录，收尾只是「封口」这个补充动作。** 新话题立刻记 open、有进展随手更新，不要等到收尾才补——否则对话突然中断（用户走了、被迫 /new、断网）事件就丢了。

对话自然收尾时，把仍在 open 的话题更新为 closed（整理最终摘要），并把产出的决策关联进去。

同时判断事件的关系：这个事件产生了什么决策（事件 → 决策「产生自」）？和之前哪些事件有关（事件 → 事件「影响」）？详见 `.ocms/rules/_sync_event.rule.md`。

## 设计原则

1. **惰性触发，不打断**：记忆读写融在自然对话里，顺手完成，不打断任务、不长篇汇报。

2. **准确优先，宁可少记**：只记真实的决策、认知、偏好，不脑补、不编造。不确定时宁可不记。

3. **识别交给 LLM，不硬编码**：什么是有意义的决策、认知怎么分类、品味怎么判断，都由你按实际情况判断，不套死板模板。

4. **记忆可演化，非一次性**：决策会被否定再更新，品味会漂移，认知会演进。维护的是活的记忆。

5. **四块各记各的，不因重叠而省略**：一条信息同时属于多块时，各块都要记。

6. **查阅优先于记录**：做决策前先查（ocms_recall / 读 cognition / 读 taste），开场先查进行中事件（ocms_event_list），再动手。
